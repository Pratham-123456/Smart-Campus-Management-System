1. Executive Summary & Architectural Overview

The XYZ University Smart Campus Management System is a full-stack, enterprise-grade university portal designed to manage core academic operations and examination lifecycles. Built for the Database Systems course, the application replaces legacy desktop paradigms with a modern, high-performance web architecture consisting of a vanilla JavaScript Single-Page Application (SPA) frontend, a Spring Boot 3.3.4 RESTful backend, and an Oracle Database 26ai Free relational database.

Core System Roles & Navigation Scope

In accordance with institutional requirements, authenticated user sessions are strictly scoped into two primary academic pillars:

  • Academics: Handles student profiles, active course registrations, offerings catalogs with live capacity checking, attendance rate tracking, and continuous assessment gradebooks.
  • Examinations: Manages centralized exam timetables (CAT1, CAT2, FAT), exam seat registrations, published scorecards with letter grade determinations, and re-evaluation petitions.

3. Backend Architecture & REST API Specification

The backend is developed with Java 21 and Spring Boot 3.3.4, following enterprise clean architecture principles. It resides in SmartCampus/src/main/java/com/campus/smartcampus/.

1. Security & Interception Layer (`config/AuthInterceptor.java`)

The application employs a defense-in-depth security approach. Because university applications handle private student records and faculty gradebooks, every request is intercepted before hitting controller logic:

  • Public Whitelist: /api/auth/**, static resources (/css/**, /js/**, /, /index.html) bypass session checks.
  • Session Enforcement: All endpoints under /api/student/**, /api/faculty/**, and /api/admin/** require an active HttpSession with an authenticated LoginResponse attribute. Unauthenticated calls receive HTTP 401 Unauthorized.
  • Role Isolation & Cross-Account Defense:
    • A student with ID 1001 attempting to call /api/student/1002/... is rejected with HTTP 403 Forbidden.
    • A faculty member with ID 201 attempting to access /api/faculty/202/... is rejected with HTTP 403 Forbidden.
    • Administrators have verified institutional oversight access across all student and faculty endpoints.

4. Business Logic Services & Relational Database Layer

1. Core Business Validation Rules (`service/`)

  • Seat Capacity Enforcement: When a student submits a registration request, StudentService.registerCourse() counts current enrollments against Max_Seats. If full, it throws IllegalStateException returning HTTP 409 Conflict.
  • Duplicate Enrollment Prevention: Re-registering for an offering already enrolled returns HTTP 409 Conflict.
  • Attendance Ceiling: FacultyService.updateAttendance() verifies that Classes_Attended ≤ Classes_Held for that offering. Exceeding classes held raises IllegalArgumentException returning HTTP 400 Bad Request.
  • Continuous Assessment Ceilings: In FacultyService.updateMarks():
    Continuous Assessment ≤ 30,    Midterm ≤ 30,    Final Exam ≤ 50
  • Authoritative Letter Grade Calculation: Exam results calculate percentage dynamically:
    Percentage = (Marks Obtained / Max Marks) × 100
    The percentage is strictly mapped against the GRADE table boundary:
    • S: ≥ 90% (Grade Point: 10.0)
    • A: 80% – 89.99% (Grade Point: 9.0)
    • B: 70% – 79.99% (Grade Point: 8.0)
    • C: 60% – 69.99% (Grade Point: 7.0)
    • D: 50% – 59.99% (Grade Point: 6.0)
    • F: < 50% (Grade Point: 0.0)
